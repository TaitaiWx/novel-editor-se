# Update recovery guardian

These are production OS-native helpers, not an Electron copy or a replacement development application. `electron-builder.yml` packages them as resources. Before every coordinated update the healthy application copies them and a SHA256-verified release artifact to a private `userData/update-recovery/<nonce>` directory, registers recovery at the **next user login**, starts the guardian, waits for its ready acknowledgement, saves the editors, then commits the handoff. The process is `/bin/sh` or Windows PowerShell, so replacing or crashing Electron cannot remove its runtime. Windows uses a short-lived bootstrap process that exits before installation: the NSIS installer's `taskkill /T` must not terminate the guardian as an application descendant.

The guardian waits until the installing application exits, then allows 180 seconds for the exact target version to acknowledge main/window/renderer health with this transaction's nonce. A missing acknowledgement (including abort/kill before application JavaScript) causes one restore attempt. Restore launch/installer exit alone never reports success; the exact previous version must acknowledge its own healthy startup. The release manifest must declare `recoveryProtocol: 1`; an older release with only `rollbackProtocol: 1` cannot make this acknowledgement and is refused as an automatic-update fallback. Existing release artifacts are not relabeled retroactively. To migrate, manually install the first signed release that actually implements this protocol; once that version and its matching manifest are published, it can protect subsequent automatic updates. An old client updating into the first protocol-capable release still uses its old update mechanism and is not retroactively protected.

The current-user login registrations are a macOS LaunchAgent plist, Windows HKCU Run value, or Linux XDG autostart entry. No root daemon/service is installed. They persist before installation and are removed after healthy acknowledgement/cancellation. On reboot a pre-restore transaction resumes at next login. A restore claim is a fully written payload published through an atomic hard link; the health acknowledgement competes for the same decision. POSIX guardians use the OS kernel lock (`lockf` / `flock`), never a PID lease or timeout-based takeover. An interrupted macOS directory publication resumes the same validated swap from its filesystem journal. A launched native installer is never blindly replayed; after guardian/installer interruption its old-version health acknowledgement is awaited and otherwise a retained failure is reported. This bounds retries; it does not promise recovery from power loss during every native installer disk operation.

| Installation | Recovery action | Required capability |
| --- | --- | --- |
| macOS signed `.app` | Verify ZIP digest, extract, verify Apple signature + same TeamIdentifier + bundle ID + exact bundle version, stage next to installed app, stop that exact executable, replace and open restored app | Parent/application writable by current user; signed production bundle; protected system installations are refused before forward install |
| Windows NSIS | Verify cached EXE digest, run NSIS with its ordinary install location and relaunch flags | Per-process `RemoteSigned` permits the bundled private local helper; global policy is never modified and enforced group policy is checked and cannot be bypassed; installer owns any UAC authorization; cancellation/nonzero exit is failure |
| Linux AppImage | Verify artifact digest, stop only processes whose launch environment names this exact image, copy/chmod and atomically rename on its original volume, relaunch | Writable original image directory; `/proc`; `sha256sum`; `flock` |
| Linux Debian | Verify package digest and installed package identity, invoke `/usr/bin/pkexec /usr/bin/dpkg --install` and relaunch | `dpkg-query`, `dpkg-deb`, `pkexec`, graphical polkit agent and **user authorization**; this is not unattended recovery |

The private transaction directory must support hard links, checked before installation. Capability is reported in update status (`mode`, `authorization`, `reboot`). No shell interpolation of installer paths, trust-bypass apt flags, `shell.openPath` handoff, development Electron copying, or code re-signing is used. Existing native recovery inside a running Electron remains available for older transactions; it yields ownership when a guardian controls the new-version failure.

Tests under `test/main/auto-updater/recovery-process.test.ts` start real OS child processes and execute `guardian.sh` against temporary fixture transactions, with harmless restore actions. They cover native SIGABRT, SIGKILL, no health, exact nonce/version acknowledgement, cancellation, delayed save, supervisor restart, competing guardians, an owner paused for more than a second, restore-decision interruption, macOS directory publication after process kill, and one-attempt failure. Debian tests verify digest rejection and literal authorized command arguments. These tests never overwrite a real application. macOS signed installation, Windows UAC/NSIS and Linux polkit/AppImage installation are platform release acceptance tests, not claimed to have run by these fixture tests.
